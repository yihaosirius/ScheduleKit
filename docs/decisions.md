# 决策记录（ADR）

一项决策一条，编号递增后不再改动；被推翻时新增一条并注明取代关系。
流水账在 [`dev-trace.md`](dev-trace.md)，这里只放**结论与理由**。

格式：`## D-<编号> <标题>` → 状态 / 背景 / 决策 / 理由 / 被否决的替代方案 / 影响。

---

## D-001 配置格式用 TOML，且全项目只有一份文件

- **状态**：采纳（2026-10-03）
- **背景**：需要一个既能被控制台就地改写、又不至于越改越乱、还要能放少量密钥的配置载体。
- **决策**：`config.toml` 单一文件；生产 `/etc/schedulekit/config.toml`（0600），开发仓库根目录。
  写入走 tomlkit 读-改-写 + 同目录临时文件 + `fsync` + `os.replace`。密钥支持环境变量覆盖，
  **环境变量优先于文件**。
- **理由**：TOML 保留注释与顺序（tomlkit），人改与程序改可以共存；单一来源消除了
  "这个值从哪来"的排查成本；环境变量覆盖让"不落盘密钥"成为可能。
- **被否决**：
  - JSON —— 丢注释、丢顺序，配置文件会退化成一坨不可读的东西。
  - `.env` + 多来源合并（`SK_*` 变量层层覆盖）—— 合并规则一多，"为什么生效的是这个值"
    就成了玄学；上一版正是因为这条被删掉。
  - 数据库 `settings` 表 —— 密钥进库、库要备份、读取还要连库，收益为零。
- **影响**：`app/config.py` 是唯一读环境变量的地方（`ENV_OVERRIDES`）。
  控制台改 `[llm]` 后热加载该段；`[server]`/`[tls]`/`[auth]` 改动需重启并在 UI 提示。

## D-002 数据库用 SQLite（WAL），迁移用手写 SQL + 序号文件

- **状态**：采纳（2026-10-03）
- **背景**：单用户个人应用，服务器只有 1.6GB 内存，且已有 4 个 Docker 容器在跑。
- **决策**：SQLite，`journal_mode=WAL` / `synchronous=NORMAL` / `foreign_keys=ON` /
  `busy_timeout=5000`；迁移为 `app/migrations/NNNN_描述.sql`，在单个事务内按序执行。
- **理由**：零额外进程、单文件备份、WAL 让控制台读状态不阻塞快捷指令写入。
  迁移是每学期一两次的量级，手写 SQL 比引入抽象更省事。
- **被否决**：
  - PostgreSQL —— 机器上虽然有容器，但为一个单用户待办再加一条常驻进程和连接池不划算。
  - Alembic —— 多一层需要理解的抽象与自动生成的不确定 diff；手工 SQL 的 diff 可读。
  - `Connection.executescript` —— 它在执行前隐式 COMMIT，会让外层事务提前提交，
    迁移中途失败就留下半个 schema（`app/migrations/runner.py` 里有注释说明）。
- **影响**：写操作必须包在 `app.db.transaction()`（`BEGIN IMMEDIATE`）里；
  库层用 `CHECK ((due_at IS NULL) <> (priority IS NULL))` 兜住"二选一"。

## D-003 任务的有序表 / 无序表由「截止时间 vs 优先级」二选一决定

- **状态**：采纳（2026-10-03）
- **背景**：需求要求"有截止时间的进有序表、有优先级的进无序表"，且两者二选一。
- **决策**：`items` 表同时保留 `due_at` 与 `priority` 两列，用 `CHECK` 强制**恰好一个非空**；
  排序规则：有序表按 `due_at` 升序，无序表按 `priority` Ⅰ→Ⅴ 分组、组内按创建时间。
- **理由**：两列而不是"一个 type + 一个 value"，让索引与排序条件都是天然可用的；
  `CHECK` 让非法状态在库层就不可能存在，服务层只需负责给出可读的中文错误。
- **被否决**：
  - 用两行/两表分别存 —— 同一条任务在两张表之间迁移要删+插，会丢 `id` 与历史。
  - 只存 `due_at`，用"有无优先级"反推 —— 无法表达"两者都没给"这种模型常见输出，
    校验会变得含糊。
- **影响**：LLM 输出后处理后，`normalize` 必须保证恰好一个非空，并在它替模型纠正时打点。

## D-004 学期周次用日期差计算，不用 ISO 周编号

- **状态**：采纳（2026-10-03）
- **背景**：提示词要注入"现在第几教学周"，并按周判断某门课今天上不上。
- **决策**：`term_week(day, start_date) = (day - start_date).days // 7 + 1`。
  开学前算出 ≤0 的值**原样返回**，由调用方识别。
- **理由**：教学周语义完全由配置的 `start_date` 决定，直觉可验证。
- **被否决**：`date.isocalendar()[1]` —— ISO 周编号在跨年（12 月底/1 月初）会跳变，
  且与"第 1 周从配置的周一算起"不是一回事。
- **影响**：`term_week <= 0` 表示假期，课表查询与提示词都要显式处理这种情况。

## D-005 时间一律 UTC 入库，补时区必须报告

- **状态**：采纳（2026-10-03）
- **背景**：用户输入、LLM 输出、课表时间三者时区来源不同，最容易出现"差 8 小时"的静默错误。
- **决策**：库内只存 UTC ISO8601；`parse_local_or_offset()` 返回 `(时刻, 是否由我们补了时区)`，
  第二项为真时调用方必须记进 overrides 并打点；只给日期时按**本地零点**解释。
- **理由**：把"我替你改过时间"变成可观测事件，是这类错误唯一的防线。
- **被否决**：静默按 `server.timezone` 补 —— 结果看起来完全正常，问题会在几天后才暴露。
- **影响**：`app/timeutil.py` 是唯一的时间进出口；渲染层才做时区换算。

## D-006 开发 trace 文档是强制约定，并用测试守住

- **状态**：采纳（2026-10-03，用户明确要求"补充一条开发时维护 trace 文档"）
- **背景**：项目会由多轮 agent 会话持续推进，没有溯源记录时"为什么当初这么写"会彻底丢失。
- **决策**：`AGENTS.md` §1 规定 `docs/dev-trace.md` 的固定字段与"同一次改动内完成"；
  `docs/decisions.md` 沉淀决策；`tests/test_trace_convention.py` 断言文档存在且字段齐全。
- **理由**：只写进文档的约定会在几轮之后被遗忘；测试失败是无法忽略的信号。
- **被否决**：只在 AGENTS.md 写一段话（靠自觉）；把 trace 混进运行时日志
  （人的叙述与机器证据混在一起，两边都读不了）。
- **影响**：每次代码改动都要追加 trace；违反时 `pytest` 会失败。

## D-007 站点端口保持 8443（不改 443）

- **状态**：采纳（2026-10-03），**取代**同日曾短暂采用的「改到 443」方案
- **背景**：上一版把站点放在 `https://canisa1ph.duckdns.org:8443`。
  重写时我一度判断"标准端口更省事"并改到了 `:443`，随后用户否决。
- **决策**：站点继续监听 **`:8443`**，Caddyfile 显式写
  `https://canisa1ph.duckdns.org:8443`。
- **理由**（两条都是**硬约束**，优先于任何"端口美观/标准"的考量）：
  1. **已有快捷指令写死了 `:8443`**。换端口要重新编辑并在手机上重新分发快捷指令，
     个别情况下还要重新授权相机权限——这是用户侧实打实的成本。
  2. **备案**：80/443 是备案相关端口。用 8443 正是为了绕开备案要求；
     改回 443 会把这个问题重新引进来。**没备案就不能碰 443。**
  另外证书目录仍从 `/etc/schedulekit/certs` 迁到 `/etc/schedulekit-tls`
  （旧目录属主是已删除的 `schedulekit` 用户，而 Caddy 要读私钥；
  证书与"应用可写的配置目录"分开，权限模型才自洽：`root:caddy` vs `schedulekit`）。
- **被否决**：
  - 改到 443 —— 用户明确否决，理由见上（快捷指令 + 备案）。
    我原来的论据是"非标端口会踩 Service Worker 作用域 / Cookie `SameSite` /
    添加到主屏幕三处坑"。这条**仍然成立**，但它属于**代价**层面，而上面两条是**约束**：
    为消掉一个可由真机验证的代价，去破坏已装好的快捷指令并引入备案要求，是不划算的交易。
  - 443 与 8443 双开 —— 双开并不能让快捷指令少改，反而多一个对外入口
    与一份需要维护的证书/站点块。
  - 只在 `docs/dev-trace.md` 里记这笔教训 —— 否决原因是 trace 是流水账；
    这种"约束优先于代价"的判断要写进 `AGENTS.md` 才会被下一轮读到。
- **代价（显式记录，不隐瞒）**：非标准端口下 Service Worker 作用域、Cookie `SameSite`、
  "添加到主屏幕"的行为都与 443 不同，需在真机确认。已用测试
  （`tests/test_config.py::test_caddyfile_listens_on_site_port` 等三条）锁住这个选择，
  防止后续被"顺手优化"掉。
- **影响**：`[server].public_url` 与 `[tls].port` 都是 8443；
  探测已确认公网 `116.62.52.66:8443` 可达（TLSv1.3 握手成功，证书 CN 正确），
  `443/80` 均为 filtered。

## D-008 Cookie 会话识别 Web UI，API Key 识别快捷指令/小组件；两者不叠加

- **状态**：采纳（2026-10-03）
- **背景**：浏览器要"一次登录长期有效"，快捷指令要"无交互可重复调用"，两者对凭据的要求相反。
- **决策**：两条互斥的凭据路径。Cookie 会话 = 签名 Cookie（`HttpOnly` + `SameSite=Lax`，
  HTTPS 下加 `Secure`）+ 写操作强制 `X-CSRF-Token`；API Key = `Authorization: Bearer sk_...`，
  **不做 CSRF 校验**，只读/可写由 `scope` 决定。会话吊销靠 `session_epoch` 自增。
- **理由**：CSRF 攻击的前提是浏览器会自动携带凭据；`Authorization` 头不会被自动携带，
  给 API Key 加 CSRF 只会让快捷指令无法工作。
- **被否决**：
  - 服务端 session 表 —— 单用户单机场景下，为"能踢会话"引入一张表与清理任务不划算。
  - 让签名覆盖负载但不覆盖 `epoch` —— 那样把 epoch 改大就能绕过"改密码踢会话"。
  - 朴素双提交 CSRF（Cookie 值 == 表单值）—— 能写 Cookie 的攻击者可两边写成同一值。
  - 给 API Key 也上 CSRF —— 快捷指令传不了（也不该传）CSRF token。
- **影响**：`app/deps.py` 的 `require_csrf` 按 `principal.kind` 分支；
  测试必须覆盖"API Key 请求无 CSRF 也能写"与"Cookie 请求无 CSRF 被拒"两侧。

## D-009 结构化输出走「强制 function calling 为主、JSON 降级为辅」三通道

- **状态**：采纳（2026-10-03）
- **背景**：设计以「不可信思想」为前提，首选 tool use；但 DeepSeek 现行文档明确：
  **thinking 模式下 `tool_choice` 为 `required` 或具名工具会返回 400**，
  且"模型没产出 function call"是无法事前探测的真实失败模式。
- **决策**：三通道按序尝试，逐级降级且**降级必须响亮**（落库 `llm_path` + WARNING 日志 +
  确认页标记）：
  1. 强制 function calling（`thinking` 关闭 + 具名 `tool_choice` + `strict: true`）
  2. JSON 结构化输出（responses 用 `text.format=json_schema`，chat 用 `response_format=json_object`）
  3. thinking 开启 + `tool_choice: auto`
- **理由**：主通道拿到的是**约束解码**结果，格式漂移最小；降级通道保证"供应商行为变化"
  不会让功能整体不可用；而把降级做成可观测事件，用户才知道这一次的结果可不可信。
- **被否决**：
  - 只做 tool call，失败即报错 —— 供应商侧的策略变化会直接让功能不可用。
  - 静默降级到"解析模型自由文本" —— 那是最难排查的一类失败，也违背不可信前提。
  - 只用 JSON mode —— 放弃 `strict` 的工具参数校验，格式漂移要靠后处理兜，成本更高。
- **影响**：`llm_path` 是 `ingest_drafts` 的列；`app/llm/structured.py` 负责编排，
  `app/llm/tools.py` 是三套请求形状的唯一真相。

## D-010 旧实例「彻底清空」，但先做一次不可逆前的归档

- **状态**：采纳（2026-10-03）
- **背景**：用户明确选择"彻底清空，从零开始"，而服务器上跑的正是上一版 ScheduleKit，
  库里已有 33 条真实任务、11 门课、13 张上传图片。
- **决策**：执行拆除，但 `deploy/legacy-teardown.sh` 强制先归档到
  `/root/legacy-schedulekit/`（可读 SQL dump + 原始 db + 上传图片 tar + 旧配置 + 旧设计文档），
  并支持 `--archive-only` 两段式执行。
- **理由**：归档成本 37MB，误删成本不可逆。"从零开始"针对的是代码与部署，
  不必然包含数据；把不可逆操作与可逆操作分开，是最基本的风险控制。
- **被否决**：
  - 不归档直接删 —— 一旦发现"某条任务还得要"就没有退路。
  - 新旧共存、验证后再切 —— 用户已明确排除，且会长期多占内存（服务器仅 1.6G）。
  - 自动恢复旧数据 —— 与"从零开始"冲突；归档只作保险，恢复是人工决定的事。
- **影响**：`/root/legacy-schedulekit/` 需长期保留；`docs/deploy.md` 记录其位置与内容清单。
