# 决策记录（ADR）

一项决策一条，编号递增后不再改动；被推翻时新增一条并注明取代关系。
流水账在 [`dev-trace.md`](dev-trace.md)，这里只放**结论与理由**。

格式：`## D-<编号> <标题>` → 状态 / 背景 / 决策 / 理由 / 被否决的替代方案 / 影响。

---

## D-001 配置格式用 TOML，且全项目只有一份文件

- **状态**：采纳（2026-10-03）
- **背景**：需要一个既能被控制台就地改写、又不至于越改越乱、还要能放少量密钥的配置载体。
- **决策**：`config.toml` 单一文件；生产 `/etc/schedulekit/config.toml`（0600），开发仓库根目录。
  写入走 tomlkit 读-改-写 + 同目录临时文件 + `fsync` + `os.replace`。密钥支持环境变量覆盖，
  **环境变量优先于文件**。
- **理由**：TOML 保留注释与顺序（tomlkit），人改与程序改可以共存；单一来源消除了
  "这个值从哪来"的排查成本；环境变量覆盖让"不落盘密钥"成为可能。
- **被否决**：
  - JSON —— 丢注释、丢顺序，配置文件会退化成一坨不可读的东西。
  - `.env` + 多来源合并（`SK_*` 变量层层覆盖）—— 合并规则一多，"为什么生效的是这个值"
    就成了玄学；上一版正是因为这条被删掉。
  - 数据库 `settings` 表 —— 密钥进库、库要备份、读取还要连库，收益为零。
- **影响**：`app/config.py` 是唯一读环境变量的地方（`ENV_OVERRIDES`）。
  控制台改 `[llm]` 后热加载该段；`[server]`/`[tls]`/`[auth]` 改动需重启并在 UI 提示。

## D-002 数据库用 SQLite（WAL），迁移用手写 SQL + 序号文件

- **状态**：采纳（2026-10-03）
- **背景**：单用户个人应用，服务器只有 1.6GB 内存，且已有 4 个 Docker 容器在跑。
- **决策**：SQLite，`journal_mode=WAL` / `synchronous=NORMAL` / `foreign_keys=ON` /
  `busy_timeout=5000`；迁移为 `app/migrations/NNNN_描述.sql`，在单个事务内按序执行。
- **理由**：零额外进程、单文件备份、WAL 让控制台读状态不阻塞快捷指令写入。
  迁移是每学期一两次的量级，手写 SQL 比引入抽象更省事。
- **被否决**：
  - PostgreSQL —— 机器上虽然有容器，但为一个单用户待办再加一条常驻进程和连接池不划算。
  - Alembic —— 多一层需要理解的抽象与自动生成的不确定 diff；手工 SQL 的 diff 可读。
  - `Connection.executescript` —— 它在执行前隐式 COMMIT，会让外层事务提前提交，
    迁移中途失败就留下半个 schema（`app/migrations/runner.py` 里有注释说明）。
- **影响**：写操作必须包在 `app.db.transaction()`（`BEGIN IMMEDIATE`）里；
  库层用 `CHECK ((due_at IS NULL) <> (priority IS NULL))` 兜住"二选一"。

## D-003 任务的有序表 / 无序表由「截止时间 vs 优先级」二选一决定

- **状态**：采纳（2026-10-03）
- **背景**：需求要求"有截止时间的进有序表、有优先级的进无序表"，且两者二选一。
- **决策**：`items` 表同时保留 `due_at` 与 `priority` 两列，用 `CHECK` 强制**恰好一个非空**；
  排序规则：有序表按 `due_at` 升序，无序表按 `priority` Ⅰ→Ⅴ 分组、组内按创建时间。
- **理由**：两列而不是"一个 type + 一个 value"，让索引与排序条件都是天然可用的；
  `CHECK` 让非法状态在库层就不可能存在，服务层只需负责给出可读的中文错误。
- **被否决**：
  - 用两行/两表分别存 —— 同一条任务在两张表之间迁移要删+插，会丢 `id` 与历史。
  - 只存 `due_at`，用"有无优先级"反推 —— 无法表达"两者都没给"这种模型常见输出，
    校验会变得含糊。
- **影响**：LLM 输出后处理后，`normalize` 必须保证恰好一个非空，并在它替模型纠正时打点。

## D-004 学期周次用日期差计算，不用 ISO 周编号

- **状态**：采纳（2026-10-03）
- **背景**：提示词要注入"现在第几教学周"，并按周判断某门课今天上不上。
- **决策**：`term_week(day, start_date) = (day - start_date).days // 7 + 1`。
  开学前算出 ≤0 的值**原样返回**，由调用方识别。
- **理由**：教学周语义完全由配置的 `start_date` 决定，直觉可验证。
- **被否决**：`date.isocalendar()[1]` —— ISO 周编号在跨年（12 月底/1 月初）会跳变，
  且与"第 1 周从配置的周一算起"不是一回事。
- **影响**：`term_week <= 0` 表示假期，课表查询与提示词都要显式处理这种情况。

## D-005 时间一律 UTC 入库，补时区必须报告

- **状态**：采纳（2026-10-03）
- **背景**：用户输入、LLM 输出、课表时间三者时区来源不同，最容易出现"差 8 小时"的静默错误。
- **决策**：库内只存 UTC ISO8601；`parse_local_or_offset()` 返回 `(时刻, 是否由我们补了时区)`，
  第二项为真时调用方必须记进 overrides 并打点；只给日期时按**本地零点**解释。
- **理由**：把"我替你改过时间"变成可观测事件，是这类错误唯一的防线。
- **被否决**：静默按 `server.timezone` 补 —— 结果看起来完全正常，问题会在几天后才暴露。
- **影响**：`app/timeutil.py` 是唯一的时间进出口；渲染层才做时区换算。

## D-006 开发 trace 文档是强制约定，并用测试守住

- **状态**：采纳（2026-10-03，用户明确要求"补充一条开发时维护 trace 文档"）
- **背景**：项目会由多轮 agent 会话持续推进，没有溯源记录时"为什么当初这么写"会彻底丢失。
- **决策**：`AGENTS.md` §1 规定 `docs/dev-trace.md` 的固定字段与"同一次改动内完成"；
  `docs/decisions.md` 沉淀决策；`tests/test_trace_convention.py` 断言文档存在且字段齐全。
- **理由**：只写进文档的约定会在几轮之后被遗忘；测试失败是无法忽略的信号。
- **被否决**：只在 AGENTS.md 写一段话（靠自觉）；把 trace 混进运行时日志
  （人的叙述与机器证据混在一起，两边都读不了）。
- **影响**：每次代码改动都要追加 trace；违反时 `pytest` 会失败。

## D-007 站点端口从 8443 改到标准 443

- **状态**：采纳（2026-10-03），**依赖用户放开 Aliyun 安全组 443**
- **背景**：上一版把站点放在 `https://canisa1ph.duckdns.org:8443`。
- **决策**：新部署监听 `:443`，证书目录迁到 `/etc/schedulekit-tls`。
- **理由**：非标准端口会同时踩到 Service Worker 作用域、Cookie `SameSite`/`Secure`
  判定、"添加到主屏幕"行为三处坑；PWA 走 8443 属于自己给自己制造问题。
  证书目录与"应用可写的配置目录"分开，权限模型才自洽（`root:caddy` vs `schedulekit`）。
- **被否决**：
  - 继续用 8443 —— 8080/8443 段被中间设备/代理拦截的概率也更高。
  - 让 Caddy 自动 ACME(HTTP-01) —— 需要 80 入站与备案条件，而 DNS-01 走 acme.sh 已经跑通。
- **影响**：`systemctl reload caddy` 不可用（Caddyfile 里 `admin off`），改配置后
  必须 `systemctl restart caddy`。
