# 推送方案调研（本期未做）

现状：小组件只能"被拉取"，不能"被通知"。iOS 的刷新调度决定了
你可能是几小时后才看到新任务。**推送要解决的就是这件事。**

本期**没有实现**，这里只留下调研结论，避免将来从零开始。

---

## 需求到底是什么

先分清三种不同的东西，它们的成本差一个数量级：

| 需求 | 例子 | 能否用小组件满足 |
|---|---|---|
| **提醒某条任务要到期了** | "电子电路作业今晚 23:59 截止" | 部分（得等到下次刷新生效） |
| **通知有新任务进草稿箱** | "刚才拍的识别好了，去确认" | 不能（只在拍照当下可感知） |
| **每天定时汇总** | "今天有 3 件事" | 可以用「提醒事项」+ 快捷指令绕 |

实务上最有价值的是**第一条**：截止时间提醒。它也是唯一"错过就不可逆"的。

---

## 三条路线

### 路线 A：本地通知（`UNUserNotificationCenter`）

**谁能做**：能跑原生代码的东西——Scriptable（有 `Notification` API）或自建 App。

**做法**：在 Scriptable 脚本里，拉取任务后为"24 小时内到期"的条目安排本地通知。

**优点**
- 完全免费、无需服务端改动
- 离线也能触发（通知由系统调度，不依赖网络）

**缺点**
- **只有脚本运行过才能安排通知**。而脚本的运行时机正是小组件刷新的时机，
  所以它没有解决根本问题：还是"等到下次刷新"
- 通知条数有上限（系统约 64 条待发通知），要自己维护队列
- 任务时间改了要重排，容易与旧通知打架

**结论**：**成本最低，但收益也最小**。适合作为"顺手加一层"，
不适合当成解决方案。

### 路线 B：ntfy 之类的自建推送服务

**做法**：服务端在任务临近截止时 `POST` 到 ntfy 的话题，手机装 ntfy App 订阅。

**优点**
- 服务端完全可控：什么时候推、推什么，都由自己的代码决定
- 无需 Apple 开发者账号、无需备案
- ntfy 可以自建，也可以用它提供的公有实例

**缺点**
- 多一个常驻组件（自建的话）或一个第三方依赖（用公有实例）
- iOS 上的 ntfy 通知走它自己的通道，可靠性和耗电不如原生 APNs
- 需要一条定时任务（另一个 systemd timer）来扫描"哪些任务该提醒了"

**结论**：**如果要做，这是最平衡的选择**。服务端已经有一个 timer
（DuckDNS 同步）可以照抄模式。

### 路线 C：APNs（原生推送）

**做法**：自建 iOS App，或用 Bark 这类现成的 APNs 转发服务。

**优点**：通知最可靠、最省电、可以带声音与角标。

**缺点**
- **自建 App 需要 Apple 开发者账号（每年 $99）**，还要处理证书与上架
- 即使只用 Bark，也要在服务端存 device token 并适配它的接口
- 服务端要维护一条"设备"模型，而本项目目前是**单租户无设备概念**的

**结论**：**收益最高但成本也最高**。对一个个人待办应用，$99/年 换
"更可靠的提醒"是否值得，取决于你自己。如果已经有付费账号，这条路可行。

---

## 建议

按投入产出排序：

1. **先做路线 A 的轻量版**：在 Scriptable 脚本里，为 24 小时内到期的任务安排本地通知。
   成本是几十行 JS。
2. 如果发现"还是经常错过"，再上**路线 B**（ntfy）：
   - 服务端加一个 `reminder` service：扫描 24 小时内到期且未完成的任务
   - 加一个 timer，每 30 分钟跑一次
   - 用一个 `notified_at` 字段记录"这条已经推过了"，避免重复轰炸
3. **路线 C 只在已经有开发者账号时才考虑**。

## 如果要做路线 B，服务端要改什么

记在这里，避免将来重新设计：

```sql
-- 0002_add_reminders.sql
ALTER TABLE items ADD COLUMN notified_at TEXT;      -- 最后一次推送时间
ALTER TABLE items ADD COLUMN remind_before_minutes INTEGER NOT NULL DEFAULT 1440;
```

```toml
# config.toml 新增段
[notify]
provider              = "none"   # none | ntfy
ntfy_url              = "https://ntfy.sh"
ntfy_topic            = ""       # 建议用一个长得像随机串的话题名
remind_before_minutes = 1440     # 默认提前 24 小时
repeat_minutes        = 720      # 逾期未完成后多久再推一次
```

关键设计点（都是踩过才会想到的）：

- **必须记录 `notified_at`**。没有它，每轮扫描都会把同一件事再推一次，
  而"被自己的提醒轰炸"会让人直接关掉通知。
- **推送必须幂等**。ntfy 的请求可能超时，重试不能变成两条通知——
  用 `notified_at` + 一个时间窗口来判断。
- **话题名要够随机**。ntfy 的公有实例上话题名就是"密码"，
  别人猜到就能读到你的任务标题。
- **不要在推送正文里带任务详情**。iOS 锁屏通知默认会显示正文，
  而任务标题里可能有学号、群名之类的东西。正文只写"有任务临近截止"，
  详情留到打开 App 看。

## 与现有设计的关系

- 提醒**不需要**改 `items` 表的主结构，加两列即可
- 提醒逻辑应当落在 `app/services/`（可脱离 HTTP 单测），而不是 router
- 按项目约定（`AGENTS.md`），新增的推送触发**必须打点**：
  `notify.sent` / `notify.skipped` / `notify.failed`，
  否则"为什么没收到提醒"完全无从查起
